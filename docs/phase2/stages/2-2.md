# 阶段 2.2 · 核心交易闭环（mock 支付）

> 归档日期：2026-08-24 ｜ 阶段：✅ 完成
> 续接依据：本归档 + `进度总表.md` + `phase2/design/README.md`；不靠对话记忆。

## 交付物

`server/` 后端核心交易闭环：顾客登录 → 扫码签名菜单 → 下单 → 预下单 → mock 支付回调 → 订单已支付，全链路可 curl 走通，含三道幂等防线与防篡改金额校验。

| 项 | 内容 |
|---|---|
| 鉴权 | `internal/auth/jwt.go` 顾客 JWT `{cid,ch,sid}`（HS256）+ `middleware.CustomerAuth`（Bearer） |
| 签名 | `pkg/qrsign`：QR 原文 `s{shop}.t{table}.v{version}` HMAC-SHA256，常量时间比较；菜单接口强校验（dev 提供 `/api/dev/table-sig/:tid` 取合法签名） |
| 支付抽象 | `internal/pay`：`PaymentGateway` 接口（Prepay/VerifyNotify/QueryOrder/CloseOrder/Refund）+ `GatewayRegistry` + `MockGateway`；金额 int64 分；回调原文入 `payments.callback_raw` 存档 |
| 下单 | `service/OrderService.CreateOrder`：服务端重算金额（菜价×数量 + prepay 首单按人项）、沽清二次校验（20002）、会话开台/快照 pay_mode + 桌台置 occupied（同事务）、`genOutTradeNo()` 唯一单号 |
| 支付入账 | `HandlePaidSuccess`：Redis 锁 `pay:lock:<out_trade_no>`(30s) → 幂等出口（已成功直接返回）→ 金额校验（不符置 manual + 30003）→ 事务订单置 paid + 插支付成功记录 → 唯一索引冲突置 manual + 30004 → 事务外落 print_tasks |
| 状态机 | `service/order_state.go`：prepay/postpay/frontend 三条主干（7.2），`InitialStatus`（prepay→pending，其余→unsettled）、`AssertTransition` |
| 配置 | 新增 `SHOP_ID`（单租户店铺常量）、`JWT_CUSTOMER_TTL_HOURS`（读 .env.example 既有变量） |
| 路由 | `/api/auth/login`、`/api/tables/:tid/menu`（公开）；`/api/orders`、`/api/pay/prepay`（顾客 JWT）；`/api/pay/notify/mock`（mock 开关挂载）；`/api/dev/table-sig/:tid`（仅 dev） |

## 验收证据（curl 全链路）

1. `POST /auth/login {channel:"wechat", code:"openid_test_01"}` → `{code:0, token, customer_id:1}`。
2. `GET /dev/table-sig/1` → 合法 sig；`GET /tables/1/menu?sig=…` → 桌台+分类+菜品（含 is_sold_out）+按人项；**无签名 → 20001「桌台不存在或签名无效」**。
3. `POST /orders {tid:1, pax:2, items:[{dish_id:1,qty:1},{dish_id:3,qty:2}]}` → `total_amount:25400`；psql 核对：宫保鸡丁 46×1 + 剁椒鱼头 98×2 + 餐位费 5×2 + 湿巾 1×2 = **254.00 元**（首单按人项正确计入）。
4. `POST /pay/prepay {order_id:1, channel:"wechat"}` → mock 调起参数（out_trade_no/amount/subject=悦点）。
5. `POST /pay/notify/mock {amount:25400}` → `{handled:true}`；psql：订单 `paid`+paid_at、payments 恰 **1 条 success**、会话 active、桌台 A01 派生 `occupied`。
6. **重复回调**（同单号再发）→ 幂等，payments 仍 1 条，无重复入账。
7. **错误金额**（新单回传 amount:1）→ `30003「回调金额与服务端不符」`，订单置 `manual`，0 笔支付。
8. **沽清拦截**：点夫妻肺片(id=9) → `20002「已沽清」`；**无 token 下单 → 40000 未登录**。

## 关键实现决策

- **mock 回调 = 真实渠道同一内部处理**（设计 3.2/约束⑥）：`MockGateway.VerifyNotify` 只做「报文解析」，产出 `pay.NotifyResult`（含 Channel），后续 `HandlePaidSuccess` 与真实渠道逐字节相同；接入微信只需新增 `WechatGateway` 替换适配段。
- **幂等顺序**：Redis 锁先抢 → 内存态幂等出口 → 事务唯一索引兜底；唯一冲突（23505）按「重复支付」置 manual + 告警，符合 6.10。
- **回调必回 200 信封**：即使金额不符/重复支付也回 200 + 业务错误码，阻止渠道无限重试（对账与告警在 2.4 落地）。
- **顾客 SID**：单租户部署下 `sid` 取 `SHOP_ID`；多店版本在阶段 3 顾客端联调时按扫码桌台的 shop 重签。
