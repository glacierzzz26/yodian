## 设计缺口修正（对照现状发现，已定稿）

- **会话「已结账」态落地**：2.3 实现账单支付后仅解锁会话（保持 active），与设计 3.7「支付成功→会话 settled」不符 → 本次修正为事务内置 `settled`；`CloseSession` 接受 `active|settled`；`ensureSession` 遇 settled 拒绝开新台（防双会话），错误码 20017。
- **六口径对账口径细化**：per-head 折入账单不折入订单，若用「订单应收 − 支付实收」恒有账单按人项缺口 → 应收口径改为**订单直付（bill_id IS NULL 的已支付订单）+ 已支付账单（含 closed 归档）**，`diff=0` 才为平（冒烟验证 26400=26400）。
- **`bills.pay_channel` / `operator_id`**：前台收银入账时一并落渠道与操作员，支撑 5.3 现金/POS 对账拆分。
- **限流 Redis 异常降级**：`RateLimitBy` 在 Redis 故障时放行，避免限流拖垮业务（16.3 意图）。

## 关键实现决策

- **支付锁单一持有点不扩散**：2.3 确立的「锁在顶层 HandlePaidSuccess 获取、委托方法不再加锁」保持；BillPay 是前台收款新入口，不经过支付回调管线，用 `locked_for_bill` 条件更新独占会话即可（无回调重入）。
- **recon 与 API 金额同单位（分）**：DB numeric 存元，SQL 内 `×100::bigint` 折分，与其余端点 cents 一致，避免前端换算错位。
- **限流键维度**：admin 按 `operator_id`（16.3 表），下单/预支付按 `customer_id`，登录按 IP；`RateLimitBy` 支持自定义 keyFunc。
- **操作日志不阻断业务**：`RecordAudit` 写库失败仅记日志，敏感操作照常完成（追责兜底依赖 audit_logs，正常路径必写）。
- **`refunds.status` 语义**：退款端点返回的是**退款记录**状态（`success`），订单新状态在 `orders.status`（`refunded`/`partially_refunded`）——契约字段已写清。
