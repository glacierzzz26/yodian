## 一、⛔ P0 · 阻断上线

### P0-1 顾客端系统性越权（IDOR），JWT 已签 `SID` 却从未消费  ✅ 已修

> **修复说明（2026-09-15）**：评审的「消费 `SID` 即可修复」**根因有误**——顾客 JWT 的 `SID` 是 **`shop_id`**（设计方案 16.2：`{cid, ch, sid:shop_id, exp}`），**不是会话 id**，消费它不能判定会话归属。正确修法为**会话归属断言**：
> - 新增 `table_session_members` 参与表（迁移 `0006`，含存量订单回填）+ 模型 `model.TableSessionMember` + 守卫 `service/session_guard.go:assertSessionMember`。归属 = 「该顾客是会话成员」。
> - 六处会话端点（`SessionOrders`/`UpdatePax`/`BillPreview`/`CreateBill`/`CancelBill`/`CallWaiter`）的 service 方法签名的 `customerID` 入参 + 首行断言；`Prepay` 的 bill 分支加 `h.bills.AssertMember`。
> - 「非成员」与会话不存在**返回同一错误码 `ErrSessionInvalid`(20008)**，避免构成 sid 枚举预言机。
> - 成员写入两条：下单事务内 `addSessionMember`；新端点 `POST /tables/:tid/join`（契约补充，`service.JoinSession`）扫码即入。后者也是 P1-3 拼桌互见的前提。

**现象**：以下端点只校验 `session_id` 是否存在（service 层仅 `shop_id + id`），**不校验该顾客是否属于该会话**：

| 端点 | handler | 后果 |
|---|---|---|
| `GET /sessions/:sid/orders` | `handler/customer.go:397` → `service/order.go:417` | 任意顾客 JWT 可枚举 sid，读取**整桌所有订单明细、金额、customer_id、渠道** |
| `PATCH /sessions/:sid/pax` | `handler/customer.go:412` → `order.go:474` | 改他人桌就餐人数 |
| `GET /sessions/:sid/bill/preview` | `handler/customer.go:433` | 读他人账单金额 |
| `POST /sessions/:sid/bill` | `handler/customer.go:207` | 对他人会话发起结账（抢锁） |
| `POST /sessions/:sid/bill/cancel` | `handler/customer.go:448` | **取消他人会话的结账锁** |
| `POST /sessions/:sid/call-waiter` | `handler/customer.go:546` | 冒名呼叫服务员 |

另：`POST /pay/prepay` 的 **bill 分支无归属校验**（`handler/customer.go:264-295`），任意顾客可为任意 `bill_id` 预下单。

**根因**：JWT payload 里的 `SID`（会话 id，`auth/jwt.go:17`）**全仓库 0 处消费**（`grep 'GetInt64("sid")'` 无结果）。本可用于限定会话归属的字段被浪费。对比：`OrderStatus`（`order.go:574`）和订单侧 `Prepay`（`customer.go:303`）**做了**本人校验，说明作者有意识，但只覆盖了一部分。

**修法建议**：在 `service` 层为所有 `/sessions/:sid/*` 入口加「会话归属断言」——至少要求 `order.session_id` 下存在 `customer_id = cid` 的订单；或引入会话参与表（`table_session_members`）。`SID` 另可用于快速短路。

### P0-2 角色越权：后厨可免支付出餐、收银员可绕过退款  ✅ 已修

> **修复说明（2026-09-15）**：`service/order_state.go` 新增 `kitchenTransitions`（后厨仅 `paid→preparing→served`）、`cashierForbidden`（退款态 + 核销态）、`ownerDirectForbidden`（退款态）与 `AssertRoleTransition(role,payMode,from,to)`：先 `AssertTransition` 再做角色二次收紧，未知角色一律拒。`ChangeOrderStatus` 增 `role` 入参并改调 `AssertRoleTransition`；`handler/admin.go` 的 `ChangeOrderStatus` 与 `KdsMove` 均传 `c.GetString("role")`。退款态唯一写入口仍为 `RefundService`（其内部用 `AssertTransition`，不受影响）。已核查 `merchant-web` 仅发 `preparing`/`served`，**不破坏现有前端调用**。

路由权限分组本身正确（`router/router.go:88-120`），但**状态机未按角色细分可达状态**，导致跨权：

- **后厨可置未付订单为已支付**：`kitchen|owner` 组的 `POST /admin/kds/:id/move`（`router.go:117`）直接复用 `ChangeOrderStatus`（`admin.go:250`），而 `prepayTransitions["pending"]["paid"]=true`（`order_state.go:9`）→ 后厨一个请求即可把**未支付的先付订单**标为 `paid`，白吃出餐。
- **后厨可核销/假收款后付单**：`postpayTransitions["unsettled"]={paid,voided,written_off,manual}`（`order_state.go:22`）→ kitchen 可把后付订单标 `voided/written_off`（免单）或 `paid`（假收款）。
- **收银员可绕过 owner 退款通道**：`prepayTransitions["paid"]={preparing,refunded,partially_refunded,manual}`（`order_state.go:10`），而 `POST /orders/:id/status` 是 `cashier|owner`（`router.go:95`）→ 收银员调 `ChangeOrderStatus(...,"refunded")` 即可把订单标为已退款，**不经过 `RefundService`、不调网关、不写 `refunds` 表、无审计**。结果：订单显示已退款，而对账 `Recon` 的退款额恒为 0。

**修法建议**：`ChangeOrderStatus` 增加角色入参，按 16.2 权限矩阵收紧可达状态；`refunded/partially_refunded` 只能由 `RefundService` 写入；`KdsMove` 只允许 `preparing/served`。

### P0-3 退款可被负数刷额度  ✅ 已修

> **修复说明（2026-09-15）**：重构 `RefundOrder`。金额 `0` 仍表示全额，否则必须 `0 < amount <= refundable`，否则 `30008 "退款金额非法"`（负数/超额不再透传）。事务边界改写：`db.Transaction` 内先 `First` 订单（`clause.Locking{Strength:"UPDATE"}` 行锁）→ 事务内重算 `alreadyRefunded`（含 `pending`）→ 校验金额/状态 → 插 `refunds(pending)` → 置订单状态；**提交后**才调网关（成功→`success`，失败→`failed` + 回退订单状态，存根保留供审计）；线下渠道（cash/pos/scan）直接 `success`。`alreadyRefunded` 的 `Scan` 错误改为显式返回（`ErrInternal`）。行锁 + `pending` 计入 → 并发部分退款总和不再超实收。

`service/refund.go:58-61`：

```go
amount := model.Money(req.Amount)
if amount == 0 || amount > refundable {
    amount = refundable
}
```

传入 `req.Amount = -100`：不等于 0、也不大于 refundable → **两分支都不命中，`amount` 保持负数** → mock 网关直接成功（`pay/mock.go:75`）→ 写入负数 refund → 下次 `alreadyRefunded`（`refund.go:110`）求和变小 → **可反复退款**。

附带问题：`refund.go:63-101` 是**先调网关再校验状态**，状态校验失败或事务失败则钱已退无记录；`alreadyRefunded`（`refund.go:113`）的 `Scan` 错误被丢弃。

**修法建议**：`amount` 必须 `> 0 && <= refundable`，否则报错；退款调用与状态校验/写库统一在一个受行锁保护的事务边界内。

### P0-4 生产环境默认开放 Mock 支付回调 + JWT 默认密钥  ✅ 已修

### P0-5 真实支付网关完全不存在  ⬜ 未修（阶段 4 主体，本轮不做）
